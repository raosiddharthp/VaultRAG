01 — Why Now

Four conditions finally aligned.

The manufacturing knowledge problem has existed for decades. Thousands of pages of SOPs, manuals, and incident reports — locked in filing cabinets, network drives, and the heads of retiring engineers. What changed is not the problem. It is the infrastructure available to solve it.

Force — 01
Local LLMs crossed the quality threshold

Llama 3.2 3B runs on commodity hardware with instruction-following quality that was impossible two years ago. For the first time, a model capable of reading a 400-page equipment manual and answering a specific technical question runs entirely on a server in your facility — no API calls, no internet dependency.

Llama 3.2 · 2024
Force — 02
Voice input reached the factory floor

The Web Speech API is now supported natively in every modern mobile browser with no app install required. A technician standing next to running machinery can speak a query one-handed and receive a response — the only realistic input modality for the factory floor finally became infrastructure-free.

Web Speech API · Baseline 2023
Force — 03
Vector search matured into a stable primitive

ChromaDB and similar embedded vector stores turned semantic search into a single-dependency, persistent, local primitive. The retrieval layer — the part that finds the right chunk of the right manual before the LLM ever sees it — now requires no external service, no managed database, and no ongoing cost.

ChromaDB · Stable 2024
Force — 04
Data sovereignty became a procurement requirement

Manufacturing firms — particularly in aerospace, automotive, and defence supply chains — increasingly prohibit sending proprietary process data to third-party APIs. The cloud RAG market, dominated by OpenAI and Anthropic API wrappers, is architecturally excluded from these environments. The on-prem alternative is now viable.

ISO 27001 · ITAR · NDA Clauses
02 — The Problem

Two narratives. One broken system.

Every manufacturing facility has the same problem expressed in two ways: a business problem measured in downtime costs and productivity loss, and a human problem measured in frustration, risk, and physical consequence. Both are solvable with the same architecture.

The Business Problem

Knowledge locked in documents no system can query

The average mid-size manufacturer maintains 12,000–40,000 pages of technical documentation — equipment manuals, ISO-controlled SOPs, non-conformance reports, maintenance logs. This documentation exists as PDFs on network drives, printed binders on shelves, and tribal knowledge in the heads of engineers approaching retirement.

When a machine fails, the cost clock starts immediately. A technician must locate the right manual, navigate to the relevant section, cross-reference the error code, and retrieve the correct procedure — manually, under pressure, often in a noisy environment. Every minute of that search is downtime. Every wrong procedure is extended downtime.

The Human Problem

A technician who cannot afford to be wrong

Marcus has worked the floor for eleven years. He knows most of the machines by sound. But the Haas CNC just threw an E-04 fault he has not seen before, and the line is stopped. His phone has no signal strong enough for a Google search. The manual is a 380-page PDF on a laptop in the supervisor's office forty metres away.

He asks a colleague. The colleague thinks he remembers the procedure. They try it. It is not quite right. The fault clears but returns in two hours. Now it is a recurring incident, not a resolved one — and it will be documented as such in the NCR log that Quality reviews on Friday.

03 — Architecture

Three layers. One coherent contract.

VaultRAG is designed as three distinct layers with a single invariant: no data crosses the facility boundary. The mobile interface lives on the technician's phone. The intelligence runs on a server inside the plant. The documents never move.
